# DevOps Team Code of Conduct

**Module:** SET09803 — DevOps | **Group:** 12 | **Date of Production:** September 9th, 2026

---

## 1. Purpose
This document sets out how our team will work together on the SET09803 project. It covers how we communicate, how we handle code and version control, how we review each other's work, and how we deal with problems when they come up. Every team member agrees to follow it.

---

## 2. Team Principles
* **Team-First Mindset:** We work as a team. This module is not a competition. We share knowledge, help each other when someone is stuck, and measure success by the team's output, not by individuals looking busy.
* **Respect Each Other:** Everyone's time and contribution matter. No one is treated as a 'resource.' We listen, we take part when we're there, and we speak to each other professionally.
* **Ego is Not Helpful:** If we're wrong, we admit it and fix it. Feedback on our work is about improving the work, not criticizing the person.
* **Continuous Learning:** Every lab and every project task is a chance to improve how we work. If a process isn't working, we say so and change it.

---

## 3. Communication
* **Quick Questions & Coordination:** Our team WhatsApp group is fine for day-to-day coordination, quick questions, and letting each other know what's happening.
* **Decisions & Technical Documentation:** Decisions, tasks, and 'how do I do this?' information go into GitHub (Issues, README, PR comments) so they are recorded and anyone on the team can find them later. Chat is not a reliable long-term record.
* **Syncing WhatsApp Decisions:** If a decision is made in WhatsApp, we write it down in GitHub too. A decision that only exists in chat is not properly recorded.
* **Blocking Issues:** If something is stopping progress, we post it in the group with a short description of what we've already tried. If no one responds in a reasonable time, we flag it to the team lead.

---

## 4. Code, Git, and Version Control
* **Branching Workflow:** We work on branches, not directly on the main branch. The main branch should always be in a working state.
* **Atomic Commits:** We make small, focused commits. Each commit should represent one clear change. We write commit messages that explain what changed and why—not just 'update' or 'fix.'
* **Pre-Push Testing:** We test before we commit and push. Code that goes into the shared branch should build and do what we intend. If a change breaks the build for the team, we say so immediately and fix it.
* **Frequent Pushing:** We push regularly. Work that only exists locally for days is risky. We push what we have so the team can see progress and help if needed.
* **Clean Repository:** Our `.gitignore` covers build output, IDE files, and other generated files so we don't commit junk.

---

## 5. Pull Requests and Code Review
* **Informative Descriptions:** When our work is ready for feedback, we open a Pull Request and add a short description of what it does and why.
* **Timely Reviews:** We review each other's work within a reasonable time. If we can't review in time, we say so before the delay becomes a problem.
* **Objective Feedback:** Reviews focus on the code and the approach, not on the person. Comments are clear and specific. If something is good, we say so.
* **Active Author Response:** The person who opened the PR responds to review comments—either by making the change, or by explaining why they disagree with a suggestion.
* **Stale PR Escalation:** A PR that sits without review too long is flagged so it doesn't block progress.

---

## 6. Incident Management & Remediation
* **Stabilize & Revert First:** We fix or roll back first, so the team isn't blocked. Then we tell the team what happened and what we did.
* **Blameless Post-Mortem:** After the immediate issue is resolved, we briefly look at what caused it and what we can change so it doesn't happen the same way again. We focus on the process and the system, not on blaming a person.
* **Near-Miss Tracking:** Near-misses count too. If something almost went wrong but was caught, we still note it—it tells us where the process is fragile.

---

## 7. Security and Professional Standards
* **Credential & Secret Hygiene:** No passwords, API keys, tokens, or other secrets go into the repository. If one is accidentally committed, we remove it properly and rotate it immediately.
* **Dependency Management:** We only add libraries and tools we actually need and understand. We don't pull things in without knowing what they are.
* **Academic Integrity:** We submit our own work. Collaboration within the team is expected and encouraged. Copying work from outside the team, or presenting someone else's work as our own, is not acceptable.
* **Honest & Early Communication:** We are honest about progress. If something is going to be late, we say so early enough for the team to react—not after the deadline has passed.

---

## 8. Meetups and Working Together
* **Structured Meetings:** When we have a meeting or call, there's a simple agenda and a short record of what was decided and who owns what next.
* **Purposeful Live Calls:** We use live meetings for things that genuinely need real-time discussion. Status updates and reading documents aloud can usually happen in chat or in writing instead.
* **Full Engagement:** If we're in a call or pair session, we're present and engaged. If we can't be, we say so and rearrange rather than half-participating.

---

## 9. Document Governance
* **Team Kickoff:** We read this when the team forms and everyone agrees to it.
* **Milestone Review:** We revisit it after each lab or project milestone to see if anything needs to change.
* **Collaborative Iteration:** If a part of this document isn't working in practice, we raise it as a team and update it together.

---
